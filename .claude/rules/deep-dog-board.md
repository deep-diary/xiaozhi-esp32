# deep-dog 板级开发隔离规则

> 来源：`.cursor/rules/deep-dog-board.mdc`（Cursor glob: `main/boards/deep-dog/**`）
> 适用范围：所有涉及 `main/boards/deep-dog/` 的功能开发与问题修复。

针对 `main/boards/deep-dog` 的功能开发与问题修复，遵循「板级隔离、便于上游合入」原则。

## 1. 开发范围

- **优先且默认**：所有新增代码、业务逻辑、配置、文档，都放在 `main/boards/deep-dog/` 及其子目录内完成。
- **尽量不改**：避免修改 `main/boards/deep-dog/` 以外的公共/框架代码（例如 `main/boards/common/`、`main/` 根下其它模块、第三方组件等）。
- 能通过板级封装、适配、回调、弱符号、配置宏等方式解决的，不要去改公共路径。

## 2. 必须修改其它目录时

仅在经验证后确认「不改公共代码无法实现」时，才允许改动 `main/boards/deep-dog/` 以外的文件，并且：

1. **改动最小化**：只改必要行，不做顺手重构或无关清理。
2. **必须说明原因**：在更改处用注释标明为何必须改公共代码，便于后续合入上游源码时评审与还原。

推荐注释格式（中英均可，信息要完整）：

```c
// [deep-dog] 合入说明: <一句话原因>
// 背景: <不改这里会怎样 / 板级方案为何不可行>
```

示例：

```c
// [deep-dog] 合入说明: 需暴露帧回调给板级 VisionFrameHub，公共 API 原先无扩展点
// 背景: 板级无法在不改 EspVideo 的情况下订阅原始帧，已确认无虚函数/配置钩子可用
```

## 3. Agent / 开发自检

开始改代码前先问自己：

1. 能否只在 `main/boards/deep-dog/` 内实现？
2. 若要改板级外文件：是否已验证必须改？更改处是否已写清合入原因？

未满足第 2 条时，不要提交或宣称完成公共目录修改。
