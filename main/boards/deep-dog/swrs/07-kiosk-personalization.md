# 07 · Kiosk 轮播与对话个性化

| 项 | 内容 |
|----|------|
| 优先级 | P2 |
| 依赖 | [06 Immich 识别回传](./06-face-recognize-immich.md)、前端 / Kiosk、人物档案数据 |
| 代码落点 | **前端与后台为主**；设备侧仅提供「当前人物」缓存或对话上下文钩子 |
| 验收 | 识别到人后 Kiosk 轮播其照片；对话能利用个人档案 |

## 1. 背景

人脸识别不仅是「叫出名字」，还要落到家庭场景体验：

1. **客厅大屏 / Kiosk**：轮播该人物在 Immich（或 DeepDiary）中的照片。
2. **语音对话**：结合个人档案（喜好、称呼、忌讳、近期事件等）做私人定制回复。

## 2. 目标

- 前端订阅 `person/active`（或等价 WebSocket），切换轮播源到对应用户相册。
- 对话链路在「当前在场人物」有效时，注入档案摘要。
- 无人识别 / 超时后回到默认轮播与默认人设。

## 3. 范围

**包含**

- Kiosk 状态机：默认 ↔ 人物聚焦 ↔ 回退
- 档案字段约定与注入对话的方式（系统提示 / 工具参数）
- 与 Immich 相册或 DeepDiary 媒体 API 的拉取

**不包含**

- 设备推流与云台（已由 02–04 覆盖）
- Immich 内标注人物（运维流程）

## 4. Kiosk 行为需求

| ID | 需求 | 说明 |
|----|------|------|
| KIO-01 | 订阅人物事件 | 收到 `person/active` 后切换轮播 |
| KIO-02 | 轮播内容 | 该人物相册照片；无相册则展示头像/占位 + 姓名 |
| KIO-03 | 保持与回退 | 聚焦保持 T 分钟（可配，建议 5–15）；超时或显式 clear 回默认 |
| KIO-04 | 切换防抖 | 短时间多人切换时，采用「最新 matched」或「保持当前直到冷却结束」策略并写死一种 |
| KIO-05 | 与直播同屏（可选） | 同页可嵌 HLS 预览；非必须 |

## 5. 对话个性化需求

| ID | 需求 | 说明 |
|----|------|------|
| DIA-01 | 档案模型 | 至少：称呼、关系、兴趣、禁忌、备注；与 `profile_id` 关联 |
| DIA-02 | 上下文注入 | 当前人物有效时，对话请求携带档案摘要（长度上限，避免撑爆上下文） |
| DIA-03 | 无人物时 | 使用家庭默认助手人设，不编造特定成员信息 |
| DIA-04 | 隐私 | 档案不进设备明文日志；前端展示可脱敏 |
| DIA-05 | 设备协同（可选） | 设备缓存的 `face/result` 与云端会话绑定，避免「屏幕上是 A、模型当 B」 |

### 注入示例（逻辑示意）

```text
系统侧追加：
「当前在场用户：小明（儿子）。称呼：小明。兴趣：乐高、恐龙。忌讳：不要提打针。」
```

具体挂在小智/自建 LLM 的哪一层（MCP 工具 vs 服务端 session）由 DeepDiary 后端定，**板端固件 P2 可不改公共协议**，优先服务端根据 `device_id` 查「最近活跃人物」。

## 6. 验收标准

- [ ] 已知人物出镜 → Kiosk 在数秒内切到其相册轮播
- [ ] 人物离开 / TTL 到期 → 回到默认轮播
- [ ] 对话中能体现档案信息（抽检 2～3 个问题）
- [ ] 陌生人 / unknown → 不错误套用某位家庭成员档案
- [ ] 关闭识别或隐私模式时，Kiosk 与对话均不使用人物上下文
