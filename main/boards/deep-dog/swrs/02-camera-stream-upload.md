# 02 · 设备视频流上传

| 项 | 内容 |
|----|------|
| 优先级 | P0 |
| 依赖 | [01 流媒体服务验收](./01-stream-server-verify.md) |
| 代码落点 | `main/boards/diary-brain/`（推流模块优先板内） |
| 验收 | 外网或内网可稳定拉到设备相机画面 |

## 1. 背景

在 MediaMTX 已可用的前提下，基于当前 diary-brain（相机已接入 `EspVideo`）实现内网推流。上传方式不限协议细节，但需与家庭实验室推荐拓扑一致：**设备内网推，外网只拉 HLS**。

## 2. 目标

- Wi-Fi 连上后，设备可将相机画面推到 MediaMTX。
- 支持**开机自动推流**（可配置默认开/关）。
- 验收：外部播放器可拉流看到实时画面。

## 3. 范围

**包含**

- 板端采集 → 编码（若需要）→ 推 RTMP 或 RTSP
- 推流 URL / 路径可配置（NVS 或编译期默认）
- 与现有语音对话、显示等功能的基本共存（推流失败不拖垮主程序）

**不包含**

- MQTT 开关（见 [03](./03-mqtt-stream-control.md)）
- 云台、人脸
- 公网直推（设备不直连公网 RTMP）

## 4. 技术选型（建议，实现时可再评估）

| 方案 | 优点 | 缺点 | 建议 |
|------|------|------|------|
| RTMP 推 H.264 | MediaMTX 成熟、外网 HLS 链路清晰 | ESP 需软/硬编 H.264，CPU/带宽压力 | **首选调研** |
| RTSP | 与监控生态兼容 | 部分板端栈更重 | 备选 |
| MJPEG over HTTP | 实现简单 | 带宽大、非 MediaMTX 主路径 | 仅作调试临时方案 |
| WebRTC 直出 | 低延迟 | 外网与信令复杂，P0 不做 | 后续可选 |

**帧率 / 分辨率建议（P0）**

- 分辨率：≤ 640×480 或传感器可稳定输出的较低档（与 OV3660 / 当前 `EspVideo` 能力对齐）
- 帧率：5～15 fps（优先稳定，再追流畅）
- 与本地 LCD 预览、人脸检测共用相机时，需约定「单消费者 / 帧分发」策略，避免抢总线（细节可在实现时补 ADR）

## 5. 功能需求

| ID | 需求 | 说明 |
|----|------|------|
| CAM-01 | 开机可推 | 配置为默认开启时，联网成功后自动开始推流 |
| CAM-02 | 路径可配 | 推流路径默认 `diary-brain/<device_id>`，与 [00](./00-shared-infra.md) 一致 |
| CAM-03 | 失败可恢复 | 断网 / MediaMTX 短暂不可用时，按退避重试，不阻塞主循环 |
| CAM-04 | 可观测 | 日志打印推流起停、错误码；可选上报到 `stream/status`（完整协议在 03） |
| CAM-05 | 资源边界 | 推流不得导致音频唤醒/对话明显不可用；若资源冲突，推流降级（降帧）优先保语音 |

## 6. 非功能

- 内网推流延迟目标：端到端（拍到 HLS 可播）P0 先「能看」，不卡死；具体秒级指标联调后回填。
- 连续推流 ≥ 10 分钟无明显泄漏（堆/PSRAM 稳定）。

## 7. 验收标准

- [ ] 设备上电联网后，用 `https://live.deep-diary.com/diary-brain/<device_id>/index.m3u8`（或内网 HLS）可看到相机画面
- [ ] 重启设备后行为符合「默认开/关」配置
- [ ] 人为断开 Wi-Fi 再恢复，推流可自动恢复或明确停留在可重试状态
- [ ] 实现代码主要在 `main/boards/diary-brain/`，未为推流大改公共协议栈（除非另开讨论）
