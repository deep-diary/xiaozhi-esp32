# Deep-Dog 开发计划

本文档从**产品需求、实现路径、测试验收**三方面维护机器狗板型（`main/boards/deep-dog/`）的开发节奏；尽量**仅在本目录内**完成逻辑，对主项目其它板型做最小改动。

**文档角色**：随迭代更新「已完成 / 进行中 / 待办」与验收标准，便于评审与排期。

---

## 1. 产品定位与目标

| 维度 | 说明 |
|------|------|
| **核心场景** | 语音（小智 / MCP）、触摸与**网页遥控**控制四足底盘；**OV3660 局域网 MJPEG**（十.1 已完成）；**网页人脸框 + 坐标/状态**与本地识别（十.3 `face_ai/`）；后续双目/穿透、RK3588 / ROS 协同。 |
| **技术路径** | 单路 CAN + 12 个无刷关节电机；关节轨迹在本板规划，不依赖 URDF。 |
| **原则** | 新代码优先落在 `deep-dog/`；必须改主工程时仅做 Kconfig/板型分支级最小补丁。 |

---

## 2. 当前能力基线（已实现，便于对照新需求）

以下依据当前代码与 `dog/README.md`、`touch_btn/README.md` 等整理，排期时视为**基线**。

| 能力 | 模块 | 状态说明 |
|------|------|----------|
| CAN / TWAI | `can/` | 板级初始化与收发 |
| 电机协议、12 电机注册、使能、位置模式初始化 | `motor/` | 协议含运控/位置等模式枚举；整机初始化走**位置模式 + 速度限制**等参数 |
| 单腿正弦步态、站立/卧倒、机械/行走软限位 | `leg/` | 与 `GaitPlanner` 步序对齐 |
| 整机 `DogControl`、对角 Trot / 四腿同步步态切换 | `dog/` | `goForward` / `goBack`、多小步、**一大步**（半周期内多小步+间隔）、持续前进/后退任务 |
| 姿态状态机（趴下先站立再行走、持续走与单步关系等） | `dog/dog_state_machine.h` | 可供灯带/屏显 |
| 跳舞（站立 → 2× 前进一大步 → 2× 后退一大步 → 站立） | `dog/` | 时序固定，**未**接 `trajectory` 插值 |
| 语音 / MCP：`self.dog.*`、`self.chassis.*` 等 | `esp_sparkbot_board.cc` | 调用 `DogControl`，非 UART 底盘 |
| 触摸：init 开窗、小步/大步/持续走、站立/趴下 | `touch_btn/` | 与 `DogControl` 绑定 |
| 轨迹规划库（点对点、样条、插值 API） | `trajectory/` | **库已存在**，**尚未**接入大步态/跳舞主路径 |
| 动作库：晃身、横移、跳舞扩展等 | `dog/` + MCP / 触摸 | **阶段八已交付**（左右晃身、左右平移步态、编排跳舞等，见阶段八验收） |
| OV3660 + HTTP MJPEG + 内嵌控制页 | `http-server/`（`deep_dog_http_server`） | **阶段十.1 已交付**：三态采集、`/stream`、`/api/cmd` 等（见下文 10.1） |

**缺口（基线中已标记但未做）**：**人脸检测 + 本地识别 + 网页叠加与状态**（阶段 **10.3**，独立目录）；双目与内网穿透（10.2）；左转/右转等步态若仍有缺口则迭代；跳舞/大步与 `trajectory` 深度结合仍为可选优化。

## 5. 新需求分册（六～十三）

### 阶段六：最大力矩（堵转）保护

**需求**：电机侧记录堵转或异常负载时的力矩特征；先**标定**经验堵转力矩量级，再设**阈值**，超限时**失能**以保护减速器与绕组。

| 子步 | 内容 | 实现要点 |
|------|------|----------|
| 6.1 标定 | 安全环境下缓慢增加负载或卡死单轴，记录反馈帧中的力矩（协议已有 `INT2TORQUE` 等） | `motor/`：从反馈解析力矩、日志或临时 MCP 读出；**文档化**各关节典型堵转区间 |
| 6.2 策略 | 每轴滑动峰值/滤波后与安全阈值比较 | 阈值可配置（NVS / 常量）；触发后 `disable` 或进入安全态；可选仅告警不停机（调试开关） |
| 6.3 整机联动 | 单轴保护是否触发整机 `UnknownPose` / 停持续走 | 与 `DogStateMachine` 对齐，避免半瘫继续发步态 |

**测试与验证**

- 台架：单轴轻载/阻挡，确认日志力矩与 hand-check 一致。
- 保护：设定低于实测堵转的阈值，确认触发后电机失能且总线无异常风暴。
- 回归：正常行走不误触发（需滤波与持续时间条件，避免噪声误判）。

---

### 阶段七：大步轨迹插值 + 运控模式

**需求 A**：当前「一大步」= 半周期内 **N 个小步**（如 10 步）逐步下发；希望**插值加密**（例如 10→100 点），间隔同比缩小（×0.1），并扣除**报文与调度耗时**使实际轨迹更顺滑。

| 子步 | 内容 | 实现要点 |
|------|------|----------|
| 7.1 | 在 `goForwardBigStep` / `goBackBigStep`（或下层）生成密集中间关节目标 | 复用 `trajectory/` 或对每关节做线性/样条插值；**总时长**与原大步可配置一致或与 `inter_step_delay_ms` 推导一致 |
| 7.2 | 计时 | 用 `esp_timer` / `vTaskDelay` 测量单周期 CAN 发送耗时，反推最大可行频率与插值点数上限 |

**需求 B**：由「每点位置 + 速度限制」为主，改为**运控（MIT/小米式 p/v/kp/kd/tau）** 为主，提升刚性与抗扰（需与电机固件能力一致）。

| 子步 | 内容 | 实现要点 |
|------|------|----------|
| 7.3 | 协议层封装运控发送 | ✅ `MotorProtocol::controlMotor`（p/v/kp/kd）+ `initializeMotorMitMode`；`DeepMotor::setMotorMitCommand` |
| 7.4 | 上层适配 | ✅ `LegControl`/`DogControl` 内 `#if DEEP_DOG_USE_MIT_WALK` + `DEEP_DOG_MIT_DEFAULT_*`；`config.h`：`DEEP_DOG_USE_MIT_WALK`、`DEEP_DOG_MIT_VALIDATE_FL_ONLY` |

**测试与验证**

- 对比示波/录包：同一大步，插值前后机身冲击与电流尖峰。
- 运控：阶跃与斜坡下超调、稳态误差；与现位置模式 A/B 对比；**台架**可仅 FL：`DEEP_DOG_MIT_VALIDATE_FL_ONLY`，初始化后站立，按键 2/3 单步前/后验证帧与动作。
- 压力：高插值频率下 CPU 占用与 CAN 负载率。

#### 10.1 OV3660 + HTTP 实时视频 + 内嵌控制页 — **已完成**

**产品需求（已实现）**

- 设备在局域网内通过 **IP 访问网页**，观看 **OV3660 实时画面**（优先 **MJPEG over HTTP**（`multipart/x-mixed-replace`），便于浏览器零插件播放；码率与分辨率需结合 PSRAM/CPU 实测折中）。
- 同一页面提供 **若干控制按钮**，映射与语音/触摸一致的核心动作，例如：**前进、后退、跳舞、站立、卧倒、停止持续走** 等（具体列表与 `DogControl` / MCP 已有能力对齐，避免重复造语义）。
- **实现上优先复用成熟组件**：如 ESP-IDF **`esp_http_server`**、主工程已有 **`esp_video` / `EspVideo`（`boards/common`）** 与板级摄像头配置；JPEG 编码可选用 ESP-IDF **`esp_jpeg`** 或工程内已有封装，减少自研编解码路径。

**摄像头采集三态（已实现，见 `boards/deep-dog/http-server/`）**

| 状态 | 说明 | 行为概要 |
|------|------|----------|
| **Off** | 默认，省资源 | `dog_cam_http` 任务仅短睡，不 `CaptureOnly`、不编码。 |
| **PeriodicSample** | 定时巡检（≈1Hz） | 每秒 `CaptureOnly()` 一次，日志占位「人脸/检测可挂接」；**不刷 LCD**。 |
| **Streaming** | 网页 MJPEG | Worker 按约 **8fps**（可调 `stream_target_fps_`）采帧 → `image_to_jpeg` → 写入 `jpeg_latest_`；`GET /stream` 仅**读**该缓冲并 multipart 推送，**不在 httpd 内直接抓相机**。 |

网页「视频流」按钮将模式切到 **Streaming** 后，`<img src="/stream">` 拉 MJPEG；切回 **Off** 可停采减负。**注意**：与语音拍照 MCP、触摸 Explain **共用同一 `EspVideo`**，并发时可能互抢；后续可加板级互斥或合并调度。

**板级入口**：`config.h` 中 `DEEP_DOG_HTTP_SERVER_ENABLE` / `DEEP_DOG_HTTP_SERVER_PORT`（默认 `8080`）；`esp_sparkbot_board.cc` 在 `InitializeCamera()` 末尾 `Start()`。

**HTTP 路由（简版）**

| 方法 | 路径 | 作用 |
|------|------|------|
| GET | `/` | 内嵌控制页（模式按钮 + 狗动作 + MJPEG 预览） |
| GET | `/stream` | `multipart/x-mixed-replace` JPEG |
| GET | `/api/status` | JSON：`mode`、`stream_clients`、`has_jpeg`、`port` |
| POST | `/api/capture_mode?mode=` 取值 `off` / `periodic` / `stream` | 切换采集三态 |
| POST | `/api/cmd?cmd=` 取值 `init`、`forward`、`back`、`stand`、`liedown`、`dance`、`stop_walk` | 投递 `DogControl`（`dog_web_cmd` 任务执行） |

**软件架构（模块化、可多任务）**

设计目标：**采集、消费图像的算法/业务、HTTP 服务** 解耦，便于后续加人脸检测而不推翻流媒体结构。

```
┌─────────────────────────────────────────────────────────────────┐
│  Task A：图像采集（Capture）                                      │
│  从 OV3660 / V4L2 或 esp_video 取帧（YUV/JPEG）；固定节拍或阻塞读   │
│  只做「拿帧 + 必要格式」→ 写入无锁环缓 / FreeRTOS 队列（浅队列防积压） │
└────────────────────────────┬────────────────────────────────────┘
                             │ 帧描述符或 JPEG blob（建议限长、双缓冲）
         ┌───────────────────┼───────────────────┐
         ▼                   ▼                   ▼
┌─────────────────┐ ┌─────────────────┐ ┌──────────────────────┐
│ Task B：流媒体   │ │ Task C：`face_ai` │ │ （可选）JPEG 编码     │
│ HTTP MJPEG 推送  │ │ 十.3 检测/识别任务 │ │ 若采集为 RAW 则放采集侧 │
│ 读最新帧或队列   │ │ 见下文 10.3       │ │ 或单独 worker 降低耦合 │
└────────┬────────┘ └─────────────────┘ └──────────────────────┘
         │
         ▼
  esp_http_server：GET `/` 控制页 + GET `/stream` MJPEG；
  POST `/api/cmd` 或 WebSocket 下发「动作枚举」→ **经队列交给 dog 执行线程**
```

**要点说明**

| 模块 | 职责 |
|------|------|
| **采集任务** | 独占摄像头资源；失败重试与帧率统计；不向 HTTP 直接耦合。 |
| **流媒体任务 / httpd 工作项** | 将最新 JPEG 组装 multipart 响应；控制**单客户端或多客户端**时的带宽（可限 1 路或降帧）。 |
| **人脸检测/识别（后续）** | **独立任务**：从队列取帧或与流媒体**只读共享**最新缓冲（注意缓存一致性）；算法可选 ESP-DL / 工程已有 AI 组件，避免阻塞 HTTP 发送路径。 |
| **网页遥控** | 静态 HTML/JS 可嵌入 SPIFFS/嵌入 C 数组；按钮 → REST **POST**（或 WS）；**禁止在 httpd 回调里直接长时间调用 `DogControl`**，应投递到 **专用运动命令队列**，由已有 dog 所在任务上下文或统一 `dog_cmd` 任务执行，保证与 CAN 时序、状态机线程安全。 |

**测试与验证**

- 浏览器：Chrome / Safari 手机端同 Wi‑Fi 拉流 ≥30s 无异常重启；延迟主观可接受。
- 压力：同时打开控制页 + 拉流，观察看门狗与堆剩余。
- 遥控：各按钮与语音/触摸不冲突时的行为（建议：**网页与 MCP 同级**，或文档约定优先级）。
- 为阶段 **10.2 内网穿透** 预留：对外只暴露 HTTP 端口时需注意**简易鉴权**（token/query）防误扫。

**状态**：代码已落地于 `main/boards/deep-dog/http-server/`；板级由 `DEEP_DOG_HTTP_SERVER_ENABLE` 等开关控制。后续视觉算法**不**挤占 `http-server` 内逻辑，而是通过 **10.3 独立 `face_ai/` 模块** 对接。

#### 10.3 人脸检测、本地识别与网页可视化（**当前迭代 / 待开发**）

**产品需求**

- 提供**可开关**的人脸能力：开启后，在**网页视频流**上能看到**人脸框**；同一页面**实时**展示 **人脸中心坐标**（建议归一化到 `[0,1]` 或像素坐标并注明分辨率）、**是否检测到人脸**、人脸数量等，为后续 **人头/人脸跟踪**（云台或机身微调）预留接口。
- 人脸相关能力分两层：**检测**（框与几何）与**本地识别**（同一用户、少量注册人脸等，后续迭代）；二者均放在**新建独立目录**中，与 `http-server` 解耦、便于测试与替换模型。

**推荐目录 layout（开发工程师按此建模块）**

```
main/boards/deep-dog/
├── http-server/              # 已有：HTTP、MJPEG、狗指令
└── face_ai/                  # 新建：人脸检测 + 本地识别（建议本目录内再分子文件/子模块）
    ├── README.md             # 数据流、依赖模型、内存占用、与 http-server 对接说明
    ├── face_ai_types.h       # 检测结果结构体：bbox、中心点、置信度、track_id（可选）
    ├── face_detect.*         # 检测推理封装（输入帧格式、缩放、NMS）
    ├── face_recognize.*      # （二期）本地特征/分类，依赖检测结果
    ├── face_ai_task.*        # FreeRTOS 任务：订阅帧 → 检测 → 可选识别 → 更新共享状态
    └── face_ai_bridge.*      # 可选：对 http-server 暴露的薄封装（注册回调 / 读最新结果）
```

- **禁止**在 `deep_dog_http_server.cc` 内堆叠推理代码；允许**最小改动**：增加「取最新 `FaceFrameMeta`」「是否在 JPEG 上画框」的钩子，或**并行**一路 **SSE / WebSocket** 推送 JSON（见下文方案 B）。

**软件架构（与 10.1 衔接）**

| 方案 | 视频上的框 | 页面上坐标/状态 | 优点 | 注意 |
|------|------------|-----------------|------|------|
| **A：服务端画框** | 在编码 **前** 于 YUV/RGB 上画矩形，再 `image_to_jpeg` 输出 | 同页用 **短轮询** `GET /api/face` 或 **SSE** 推 JSON | 浏览器端简单，任意 `<img src=/stream>` 即带框 | JPEG 编码多一次、CPU 略高；需线程安全地传递「最新检测」与「待编码帧」对齐 |
| **B：浏览器 Canvas 叠加** | `<canvas>` 与视频同尺寸叠在 `<img>` 上画框 | **WebSocket 或 SSE** 推送 `{faces:[{cx,cy,w,h,norm...}], has_face, ts}` | 服务端可不重编码视频流，灵活 | 前端需同步分辨率与坐标系；横竖屏与 scale 要一致 |

**推荐**：首版可采用 **B（SSE + Canvas）** 降低与现有 MJPEG 管道耦合；若产品要求「录屏即带框」再增加 **A** 或双轨。

**处理流水线（任务划分）**

1. **采集与 JPEG**（现有 `dog_cam_http` / Streaming 路径）：继续负责 `CaptureOnly` →（可选缩放）→ 编码；**不向人脸任务送 JPEG**，尽量送 **YUV 或 RGB 指针+stride**（与 `EspVideo` 输出一致），避免重复解码。
2. **`face_ai` 任务**（新建）：  
   - 输入：与流**同频或降频**（如流 8fps、检测 4fps）的帧引用或拷贝小块；  
   - 输出：线程安全的 **`FaceDetectionResult`**（时间戳、图像宽高、0..N 个人脸框与中心）；  
   - **识别**（二期）：在检测框内裁图 → 特征提取 → 与本地注册表比对 → 写入 `person_id` / 相似度。  
3. **HTTP 层**：新增例如 `GET /api/face`（JSON 快照）、`GET /events/face`（SSE）或 `WS /ws/face`；控制页增加「启用人脸」开关 → `POST /api/face_enable`。
4. **与狗控制隔离**：人脸结果仅通过**只读 API** 或**将来**单独的跟踪任务队列影响 `DogControl`，本阶段**不要求**自动跟脸。

**复用与组件**

- 可参考同仓库 **`main/boards/deep-thumble/app_ai/`**（如 `face_detect_core.cpp`、`task_face_ai.cpp`）的任务划分与 ESP-DL / 模型加载方式，**按需移植**到 `face_ai/`，避免 deep-dog 与 thumble 编译强耦合时可抽公共组件到 `boards/common`（第二阶段优化，非必须）。
- 模型格式、Flash 分区、PSRAM 要求写在 `face_ai/README.md`。

**配置项（建议）**

- `config.h` / Kconfig：`DEEP_DOG_FACE_AI_ENABLE`、检测输入分辨率上限、推理间隔 ms、是否默认开启网页叠加等。

**测试与验收**

- 功能：开关关闭时零额外 CPU；开启后浏览器可见框与数值更新延迟小于约 500 ms（目标值，可按实测温调）。
- 正确性：无人脸时 `has_face=false`、坐标区为空；多人脸时数量与框一致。
- 稳定：长时间拉流 + 人脸开关反复切换无泄漏、无看门狗；与语音拍照 MCP、Explain 触摸**抢相机**时行为符合板级文档（可文档化「人脸仅 Streaming 下启用」等策略）。
- 安全：识别结果若含个人信息，仅局域网使用；后续外网需配合 10.2 鉴权。

#### 10.2 双目推流与内网穿透（延续原规划）

**需求**：左右摄像头以 **HTTP/MJPEG 或 RTSP** 等形式访问；**内网穿透**在外网低延迟查看（延迟与码率需实测）。可在 **10.1 单路架构** 上扩展第二路采集任务或双通道队列，或按资源情况将第二路放到 RK3588（与阶段十一协调）。

| 子步 | 内容 | 实现要点 |
|------|------|----------|
| 10.2.1 | 第二路采集与编码 | 评估 ESP32 双路 JPEG 同时编码；不足则 3588 拉流 |
| 10.2.2 | 双路服务 | 双端口或单页双画面；鉴权（token） |
| 10.2.3 | 穿透 | frp / cloudflare tunnel 等；文档写明端口与协议 |

**风险**：ESP32 双路高清同时编码压力大，可能需 **RK3588 做相机主机**（与阶段十一合并架构决策）。

### 阶段十一：RK3588 CAN 与小智通讯

**需求**：RK3588 与当前小智（ESP32）通过 **CAN**（或 CAN-FD）交换高层指令、状态、传感器摘要，形成异构计算分工（规划/视觉在 3588，实时关节在 ESP32）。

| 子步 | 内容 | 实现要点 |
|------|------|----------|
| 11.1 | 帧定义 | 与电机协议 ID 空间隔离（不同 CAN ID 段或网关） |
| 11.2 | ESP32 侧 | TWAI 双通道或单总线网关策略；接收 3588 目标、回传里程/电量/IMU 摘要 |
| 11.3 | 3588 侧 | SocketCAN 用户态节点；与 ROS 可同进程或桥接 |

**测试与验证**

- 环回与误码率；高负载下与电机帧共存是否丢包。
- 安全：非法指令过滤、看门狗。

---

### 阶段十二：ROS 状态/控制反馈与 rviz 显示

**需求**：将实时控制指令或关节/机身状态反馈到 **ROS**，在 **rviz** 中可视化（模型可用简化 URDF 或 marker）。

| 子步 | 内容 | 实现要点 |
|------|------|----------|
| 12.1 | 桥接位置 | 优先在 RK3588 上跑 `ros2` 节点，通过 CAN/TCP 收 ESP32 状态；或 ESP32 侧 Wi‑Fi `ros_serial`/`micro_ros`（资源占用需评估） |
| 12.2 | 消息 | `sensor_msgs/JointState`、`geometry_msgs/Twist`（若适用）、自定义 `DogStatus` |
| 12.3 | rviz | Fixed frame、关节 display、可选 TF |

**测试与验证**

- 与真实狗动作延迟对比 rviz 显示；录 bag 复现。

---

### 阶段十三：基于 ROS 下发指令控制机器狗

**需求**：从 ROS **订阅**速度/步态/模式话题或 Action，转为 ESP32 可执行的 MCP 等价语义或 CAN 高层指令。

| 子步 | 内容 | 实现要点 |
|------|------|----------|
| 13.1 | 指令映射 | 与现有 `DogControl` API 一一对应，禁止绕过安全状态机 |
| 13.2 | 优先级 | ROS vs 语音 vs 触摸冲突策略（互斥或优先级队列） |
| 13.3 | 仿真 | 可选 Gazebo 仅在上位机，与真机共用同一话题名 |

**测试与验证**

- 急停与失能路径在 ROS 触发下仍有效。
- 与阶段六力矩保护、阶段七运控模式联合回归。

## 6. 依赖关系（更新）

```
can → motor → leg → dog → 板级 MCP / 触摸
         ↘ 力矩反馈 / 运控指令（阶段六、七）
dog / leg → trajectory（阶段七大步/跳舞平滑）
dog → 动作库（阶段八，已完成）
OV3660 → `http-server`：MJPEG + `/api/cmd`（**10.1 ✅**）
         ↘ `face_ai/`：检测/识别任务 ← 同源帧（YUV 优先）；→ SSE/WS/JSON + 可选画框 JPEG（**10.3**）
网页指令队列 → `DogControl`
IMU 驱动（阶段九）→ 安全与 ROS 状态（阶段十二）
视觉 10.2 / 双目 ↔ RK3588 分工决策
RK3588 CAN（阶段十一）→ ROS 桥接（阶段十二、十三）
```
